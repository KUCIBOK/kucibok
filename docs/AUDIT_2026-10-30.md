## P2 — Sécurité (hors P0)

| Constat | Statut |
|---|---|
| Limitation de débit : repli **en mémoire**, non partagé entre instances serverless → inefficace sans Upstash Redis configuré. | ⚠️ configurer `UPSTASH_REDIS_REST_*` et vérifier en prod |
| CSP du front : `'unsafe-inline'` et `'unsafe-eval'` dans `script-src` annulent l'essentiel de la protection XSS. Passer à des nonces/hashes. `X-XSS-Protection` est obsolète. | ⚠️ |

| Téléversement d'image : extension prise du nom de fichier, pas de contrôle de taille/type côté client ; vérifier les politiques du bucket `artworks` (migration 006). | ⚠️ |
| Table historique `logidoo_alerts` : policy d'insertion `WITH CHECK (TRUE)` (retirée par la migration 009 — à vérifier sur la base réelle). La nouvelle table `logistics_alerts` n'a aucune policy (service_role uniquement). | ⚠️ |

## Logistique — ce qui existe maintenant

| Route | Accès | Détail |
|---|---|---|
| `GET /logistics/track/:tid`, `GET /logistics/expeditions/track/:tid`, `GET /delivery/track/:tid` | public | statut + événements, **sans** nom/adresse/téléphone |
| `POST /logistics/expeditions` | artiste, curateur, advisor, admin | crée une expédition (numéro `KCB-TRK-XXXXXXXX`), œuvres facultatives mais contrôlées (propriété) |

| `GET /logistics/alerts`, `/alerts/stats`, `PATCH /alerts/:id/read`, `/alerts/read-all`, `POST /sync` | admin | table `logistics_alerts` — **migration `034_logistics_alerts.sql` à appliquer** |
| `GET /zones`, `GET /pickup-points`, `POST /rates`, `PUT /update/:tid` | connecté | 501 explicite avec la raison (pas de zones tarifées ni de devis séparé chez Logidoo ; schéma `/node` et statuts à confirmer) |
| `GET /logidoo/status[?check=1]`, `GET /logidoo/probe`, `GET /logidoo/webhooks` | admin | test de connexion authentifié, forme des réponses sans données personnelles, webhooks reçus (migration **037**) |
| `POST /logidoo/webhook?secret=…` | public, secret requis | à enregistrer dans le backoffice Logidoo ; payload brut conservé |
